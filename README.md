### ДЗ 2: VM (виртуальная машина на JS):

Требуется:
1 ) придумать собственный низкоуровневый язык, вырази
тельные способности которого будут достаточны для решения
простых вычислительных задач;
2 ) написать на этом языке программу вычисления фактори
ала натурального числа и программу нахождения наибольшего
общего делителя двух натуральных чисел;
3) написать на node.js виртуальную машину, исполняющую
программы, написанные на разработанном языке; иными сло
вами, написать на node.js интерпретатор, переводящий коман
ды разработанного языка в команды node.js

Получилось:
VM-ASM: Мини-инструкция
Простой ассемблероподобный язык для виртуальной машины.
 Программа — список строк, разделённых переводами строк.

- Комментарии начинаются с `#` и игнорируются.
- Пустые строки пропускаются.
- Выполнение начинается с метки `start:`, либо с первой строковой команды.
  Метка — имя с двоеточием в конце:

```asm
loop:
main:
```

Остальные команды и аргументы:

```
set addr value # mem[addr] = value
mov a b        # mem[a] = mem[b]
add a b        # mem[a] += mem[b]
sub a b        # mem[a] -= mem[b]
mul a b        # mem[a] *= mem[b]
mod a b c      # mem[c] = mem[a] % mem[b]  (ошибка при делении на 0)
output a       # вывести mem[a]
input a        # прочитать число и записать в mem[a]
jmp L          # перейти на метку/адрес L
jnz a L        # если mem[a] ≠ 0 → перейти на L
jz a L         # если mem[a] == 0 → перейти на L
```

Все аргументы — **адреса памяти** (целые числа) или  **имена меток** .
**Арность программ**

```
ARITY = {
  "set": 2, "add": 2, "sub": 2, "mov": 2, "mul": 2,
  "mod": 3, "output": 1, "input": 1,
  "jmp": 1, "jnz": 2, "jz": 2
}
```

**Примеры программ:**
Вывод константы

```
start:
    set 0 42
    output 0
```

Сложение с выводом

```
start:
    input 0
    input 1
    mov 2 0
    add 2 1
    output 2
```

Цикл от 5 до 1

```
start:
    set 0 5
loop:
    output 0
    set 1 1
    sub 0 1
    jnz 0 loop
```

### ДЗ 3: BruteForce поиск подстроки, хэши

## Test 1 — «первый, первый+второй, ...» (только паттерн `князь Андрей`)

 **Исходные данные** : файлы томов Войны и мира (`voyna-i-mir-tom-1.txt`, `...-tom-2.txt`, ...), порядок — как в `config.files`.

**Что делать** (пошагово):

1. Сформировать последовательность текстов:
   * `T1 = tome1` (файл 1).
   * `T1-2 = tome1 + tome2` (конкатенация без дополнительного символа).
   * `T1-3 = tome1 + tome2 + tome3`.
   * `T1-4 = tome1 + tome2 + tome3 + tome4` (и т. д., если есть 4/5 томов — согласно `config.files`).
2. Для **каждого** из этих `Ti`:
   * Берём **единственный** паттерн: `"князь Андрей"` (именно так, с пробелом и регистром).
   * Выполняем поиск методами:
     * `brute` (перебор, посимвольное сравнение);
     * хеш-методы: `sum`, `sumsq` (square), `poly` (polynomial).
   * Для каждого метода:
     * Запускаем N = 5 прогонов; фиксируем времена.
     * Записываем медиану времени.
     * Собираем `matches_positions` (позиции всех реальных совпадений).
     * Для хеш-методов дополнительно собираем:
       * `false_positive_collisions` — сколько раз хеш(window) == hash(pattern) но window != pattern.
       * `collision_details` — первые K (например, K = 50) случаев: `{pos, hash}`.
       * (опционально) `hash_collision_pairs` — число пар окон с одинаковым хешем (при разумном ограничении по памяти).
   * В CSV записать одну строку на метод (либо несколько — если вы хотите записывать все 5 прогонов как отдельные строки, но лучше одна строка с медианой).
3. Особенность, указанная в ТЗ: «перебор и сравнение хэшей только на первом, потом первый + второй и т.д.» — это именно то, что мы делаем: последовательные конкатенации томов. (Если же вы имели в виду сравнение хешей только на первой позиции, затем на первых двух символах — это другое; но в контексте вашего примера и таблиц очевидно, что речь о томах.)

 **Примечание/допущение** : я предполагаю, что вы хотите весь текст конкатенировать  *без разделителей* . Если нужен пробел/перенос строки между томами — сообщите; по умолчанию ничто не вставляется (это ближе к тому, как обычно хранят тексты).

## Test 2 — «все тома + несколько паттернов» (массовый тест)

 **Исходные данные** : те же файлы (все тома), и три паттерна:

* `"князь"`
* `"князь Андрей"`
* `"князь Андрей Балконский"`

 **Что делать** :

1. Для **каждого файла** (каждого тома отдельно) и также для **целого объединённого корпуса** (весь текст, все тома сконкатенированы) — запускаем тесты. То есть каждая комбинация:
   * `file = tome1`, `tome2`, ..., `tomeN`,
   * и дополнительно `file = tome1+...+tomeN` (если нужно).
2. Для **каждого** такого `file` и **для каждого** паттерна (3 варианта):
   * Выполняем `brute` + три хеш-метода, по алгоритму из Test1 (N прогонов, медиана времени).
   * Записываем в CSV всё то же, что и в Test1 (включая collision details для хешей).
3. CSV будет содержать много строк: одна строка = (file, pattern, method) запись.

 **Почему такой охват** : в ТЗ прямо сказано «перебор и хэши на всех томах + паттерны...». Это даёт представление о том, как масштабируется производительность и частота коллизий при разных объёмах текста и разной длине паттерна.

## Test 3 — «строки a...ab и ba...a с 100 раз символа a»

 **Исходные данные** : синтетические строки (не файлы):

* `text1 = 'a' repeated 100 times + 'b'`  (обозначим `a^100 b`)
* `text2 = 'b' + 'a' repeated 100 times`  (обозначим `b a^100`)

Паттерны, которые тестируем:

* `pattern1 = a^100 + 'b'` (ровно совпадает с `text1`, должен дать 1 вхождение в позиции 0)
* `pattern2 = 'b' + a^100` (ровно совпадает с `text2`, должен дать 1 вхождение в позиции 0)

 **Что делать** :

1. Для каждой пары `(text, pattern)` — запуск `brute` + 3 хеш-метода.
2. Замеряем время (N прогонов, берём медиану), считаем `false_positive_collisions` и позиции совпадений.
3. Этот тест выбран, потому что строки с большим числом одинаковых символов плохо «видны» некоторым простым хешам (например, сумма кодов/сумма квадратов) — поэтому мы ожидаем разные числа коллизий и разное поведение `poly` vs `sum`. Это иллюстрирует слабые стороны простых линейных хешей.
4. Запись результатов в `results/test3.csv`.

Формат CSV:

* `test` — номер/имя теста (`test1`, `test2`, `test3`, `interactive`).
* `file_source` — какие файлы используются (например `tome1`, `tome1-2`, `tome1-3` или «voyna_i_mir.txt»). Для тесты 1 — явно указывать набор томов (например: `tome1`, `tome1+tome2`, ...).
* `pattern_name` — `pattern1/pattern2/pattern3` или конкретный текст паттерна.
* `pattern` — сам паттерн (в кавычках, экранированный).
* `method` — `brute`, `sum`, `sumsq` (или `square`), `poly` (или `polynomial`).
* `time_ms` — время выполнения (миллисекунды). ****ИСКЛЮЧЕНИЕ ДЛЯ ТРЕТЬЕГО ТЕСТА -- ТАМ В МИКРОСЕКУНДАХ****
* `matches_count` — число найденных вхождений (реальных).
* `false_positive_collisions` — число коллизий типа (1) (хеш совпал с паттерном, но строка не равна).
* `text_length` — длина текста (символы).
* `pattern_length` — длина паттерна.
